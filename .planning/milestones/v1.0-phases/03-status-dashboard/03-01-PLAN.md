## Resolution of the open question: how `RunSummary` reaches the workflow

RESEARCH.md Open Question 1 offered (a) a CI-mode flag on the poller entrypoint that writes
`RunSummary` to a file, or (b) a separate thin script in `scripts/` that calls `run()`.

**Decision: (a) — `src/cli.ts`'s `runOnce()` writes the file, gated on the `RUN_SUMMARY_FILE`
environment variable.**

Justification:
1. `run()`'s signature and return shape are untouched, honouring the explicit precedent in
   `src/types.ts` line 64 ("Phase 2 wires email off this without changing run()'s shape (D-07)").
2. `src/cli.ts` is documented (lines 2-4) as the "thin trigger adapter" whose job is adapting
   `run()`'s result to a trigger environment. It already maps `RunSummary` to a console line and
   an exit code; serialising the same object for the CI trigger is the identical category of
   concern, in the module that already owns it.
3. Option (b) would add a *second* production entrypoint that duplicates `run()` invocation and
   fatal-error handling. `scripts/` currently holds only `capture-fixtures.ts`, a dev tool — it is
   not a production entrypoint directory, and making it one is more surface area than the change
   warrants.
4. Env-gating means `npm start` locally writes nothing: zero behaviour change outside CI.

The one gap in (a): if `run()` throws (fatal — e.g. `watches.json` is invalid), `runOnce()` never
gets a summary to write. That is handled in the workflow (Task 3) by synthesising a FAILED entry
when `run-summary.json` is absent, so `if: always()` still yields an honest runs.json record.

## `runs.json` entry schema (Claude's discretion per D-01)

Each entry is the **full `RunSummary` object as-is** (`startedAt`, `finishedAt`, `checked`,
`outcomes`, `newMatches`, `failed`, `noMatch`). It is already compact and already carries
timestamp + per-watch outcomes + counts as D-01 requires. Storing it verbatim means the
dashboard's local type copy mirrors `src/types.ts` 1:1, minimising drift.
</design_decision>

```typescript
/** Serialises a completed cycle's RunSummary to disk for the CI run-history log (D-01).
 *
 *  Deliberately NOT part of run() — run()'s signature and return shape stay untouched
 *  (precedent: src/types.ts "Phase 2 wires email off this without changing run()'s shape").
 *  src/cli.ts, the thin trigger adapter, calls this when RUN_SUMMARY_FILE is set.
 */
import { mkdir, writeFile, rename } from 'node:fs/promises';
import { dirname } from 'node:path';
import type { RunSummary } from './types.js';

/** Atomic write (tmp + rename), matching src/state/fileStore.ts's save() convention so a
 *  killed process can never leave a half-written JSON file for jq to choke on.
 *  A falsy `path` is a deliberate no-op: local `npm start` writes nothing. */
export async function writeRunSummaryFile(summary: RunSummary, path: string | undefined): Promise<void> {
  if (!path) return;
  await mkdir(dirname(path), { recursive: true });
  const tmp = `${path}.tmp`;
  await writeFile(tmp, JSON.stringify(summary, null, 2) + '\n', 'utf8');
  await rename(tmp, path);
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Recreation.gov / RIDB → poller | Untrusted upstream strings land in `RunSummary.outcomes[].reason` and `newMatches[]`, and are now persisted to a *public* `runs.json` |
| GitHub Actions runner → repo (`git push`) | Automated write to `main` with `contents: write` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Information Disclosure | `runs.json` (public file) containing `RunSummary.failed[].reason` | mitigate | `reason` is produced exclusively by `describeFailure()` in `src/errors.ts`, whose contract (line comment) already forbids emitting request headers or the `apikey` value (threat T-01-02). This plan adds no new reason source. Verified by: no `RUN_SUMMARY_FILE`-written field bypasses `describeFailure` — `runSummaryFile.ts` serialises `RunSummary` verbatim and never reads `process.env` beyond the path. |
| T-03-02 | Information Disclosure | `run-summary.json` accidentally committed | mitigate | `.gitignore` gains `run-summary.json` and `run-summary.json.tmp` (Task 2c); the commit step's `git add` names only `state.json runs.json`, never `-A`. |
| T-03-03 | Denial of Service | `runs.json` unbounded growth bloating every checkout of the 5-minute workflow | mitigate | `jq '.[-50:]'` cap (D-02), asserted by the 55-append loop in Task 3's automated verification. |
| T-03-04 | Tampering | Partial/corrupt `run-summary.json` if the runner is killed mid-write, feeding malformed JSON to `jq` (which would fail the step and lose the cycle) | mitigate | Atomic tmp+rename write in `runSummaryFile.ts` (Task 1), matching `fileStore.ts`'s existing convention; asserted by the "no `.tmp` remains" test. |
| T-03-05 | Elevation of Privilege | Workflow's `contents: write` token pushing to `main` | accept | Unchanged from Phase 2 (D-08/D-10). Scope is already least-privilege for the existing `state.json` push; adding `runs.json` to the same `git add` requires no additional permission. |
| T-03-06 | Tampering | Concurrent workflow runs racing on the `runs.json` read-modify-write | accept | The existing `concurrency: { group: poller, cancel-in-progress: false }` block serialises runs; this plan explicitly does not add a second job or concurrency group. |
</threat_model>
