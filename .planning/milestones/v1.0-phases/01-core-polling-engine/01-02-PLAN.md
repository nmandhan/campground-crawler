    - A function that succeeds on the first call is called exactly once and its value returned
    - A function that throws twice then succeeds is called 3 times and returns the value
    - A function that always throws is called exactly 4 times (1 initial + 3 retries) and the LAST error is rethrown

**`retryWithBackoff`** — D-05: up to 3 retries, exponential backoff 1s/2s/4s. Signature must accept injected `sleep` so tests run instantly:
```typescript
export interface RetryOptions {
  retries?: number;          // default 3
  baseMs?: number;           // default 1000
  sleep?: (ms: number) => Promise<void>;   // default: setTimeout-based
  isRetryable?: (err: unknown) => boolean; // default: see below
}
export async function retryWithBackoff<T>(fn: () => Promise<T>, opts?: RetryOptions): Promise<T>;
```
Default `isRetryable` (RESEARCH Pitfall 4 — retrying a 404 wastes 7 seconds and muddies the log):
- `BlockedError` -> false
- `HttpError` with status 429 -> true
- `HttpError` with status >= 500 -> true
- `HttpError` with any other status (all other 4xx) -> false
- anything else (network errors, `TypeError: fetch failed`, timeouts) -> true

Loop shape (from RESEARCH.md, extended with retryability):
```typescript
let lastError: unknown;
for (let attempt = 0; attempt <= retries; attempt++) {
  try { return await fn(); }
  catch (err) {
    lastError = err;
    if (attempt === retries || !isRetryable(err)) break;
    await sleep(baseMs * 2 ** attempt);   // 1000, 2000, 4000
  }
}
throw lastError;
```

**`fetchJson`** — one hardened request, no retry logic inside (callers wrap it in `retryWithBackoff`):
```typescript
export async function fetchJson(
  url: string,
  init?: { headers?: Record<string, string>; fetchImpl?: typeof fetch }
): Promise<unknown>;
```
Behavior, in order:
1. Call `fetchImpl ?? globalThis.fetch` with `{ headers: { ...BROWSER_HEADERS, ...init?.headers } }`.
2. If `!res.ok` -> `throw new HttpError(\`request failed: ${res.status} ${res.statusText}\`, res.status, url)`. Do NOT read the body first.
3. Read `res.headers.get('content-type')`. If it does not include `json` -> `throw new BlockedError(\`expected JSON but got "${contentType}" from ${url} (likely User-Agent/WAF block)\`, url)`. This is RESEARCH Pitfall 2: it turns "Unexpected token < in JSON" into a diagnosable message.
4. `await res.json()` inside a try/catch; on parse failure `throw new BlockedError(\`malformed JSON body from ${url}\`, url)`.
5. Return the parsed value as `unknown` — the caller zod-parses it.

Never log or embed request headers in any thrown message (threat T-02-02).

Implementation specifics:
- `resolveFacility` builds `new URL(\`${RIDB_BASE}/facilities\`)` with `query=<parkName>`, `limit=10`, `sort=Name`. Header: `{ apikey: opts.ridbApiKey }` only when the key is a non-empty string. Parse with `RidbFacilitySearchSchema.safeParse`; on failure throw `new ResponseSchemaError('RIDB facility search returned an unexpected shape', <formatted issues>)`. On `RECDATA.length === 0` throw `new FacilityNotFoundError(\`no RIDB facility matched "${parkName}"\`, parkName)`.
- `monthStart` is a `YYYY-MM-DD` string. Normalize to the first of that month and format the param as exactly `${YYYY}-${MM}-01T00:00:00.000Z`. Build this by string manipulation on the `YYYY-MM` prefix — do NOT round-trip through `new Date()` local time, which shifts across timezones and is a classic off-by-one-month bug (RESEARCH "Don't Hand-Roll" table).
- `fetchAvailabilityForRange(facilityId, start, end)`: enumerate every distinct `YYYY-MM` from `start` through `end` INCLUSIVE of the month containing `end` (note `end` is the exclusive checkout date, but a stay ending on the 1st still only needs nights before it — enumerating the extra month is harmless and safer than missing one). Fetch each month sequentially (not `Promise.all`) with a short pause between months if more than one — the project convention is ~1 req/sec against the undocumented endpoint (threat T-02-03). Return the array in chronological order.
- RIDB key handling: read from `process.env.RIDB_API_KEY` at the call site (plan 04's config loader), not inside this module — keep this module free of `process.env` reads so it stays trivially testable. Never include the key in any error message or log line.
