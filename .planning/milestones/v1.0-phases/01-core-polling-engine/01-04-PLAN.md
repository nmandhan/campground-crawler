```typescript
import { readFile } from 'node:fs/promises';
import { WatchesFileSchema } from './schema.js';
import { resolveFacility, type ClientOptions } from '../recreation-gov/client.js';
import { describeFailure } from '../errors.js';
import type { Watch, ResolvedWatch } from '../types.js';

export const DEFAULT_WATCHES_PATH = 'watches.json';

export interface Logger { info(msg: string): void; warn(msg: string): void }

export async function loadWatches(path?: string): Promise<Watch[]>;

export interface ResolveResult {
  resolved: ResolvedWatch[];
  failures: Array<{ watchId: string; reason: string }>;
}
export async function resolveWatches(
  watches: Watch[],
  opts?: ClientOptions & { logger?: Logger }
): Promise<ResolveResult>;

export async function loadResolvedWatches(
  opts?: ClientOptions & { path?: string; logger?: Logger }
): Promise<ResolveResult>;
```

Implementation specifics:
- `loadWatches`: `readFile(path ?? DEFAULT_WATCHES_PATH, 'utf8')`. On ENOENT throw `new Error(\`watches config not found at ${path} — copy watches.example.json to watches.json and edit it\`)`. `JSON.parse` in a try/catch -> `new Error(\`watches config at ${path} is not valid JSON: ${msg}\`)`. Then `WatchesFileSchema.safeParse`; on failure throw an Error listing each issue as `${issue.path.join('.')}: ${issue.message}` joined by `; `. Config errors are fatal for the run (there is nothing to poll) — unlike per-watch check failures, which are isolated.
- `resolveWatches`: build `const cache = new Map<string, Promise<ResolvedFacility>>()` keyed by the lowercased trimmed `parkName`, storing the in-flight promise so concurrent identical names share one request (D-02 memoization). For each watch:
  - If `watch.facilityId` is set, use it with `facilityName: watch.parkName` and make no RIDB call.
  - Otherwise `await` the cached `resolveFacility(watch.parkName, opts)`.
  - Wrap each watch in try/catch; on error push `{ watchId: watch.id, reason: describeFailure(err) }` into `failures` and continue to the next watch (D-06: a bad name never aborts the whole run).
  - On success `logger.info(\`resolved "${watch.parkName}" -> facility ${facilityId} (${facilityName})\`)` once per unique name; if `alternatives.length > 0` also `logger.warn(\`  other RIDB matches for "${parkName}": ${alternatives.join(', ')} — set "facilityId" in watches.json if this resolved to the wrong campground\`)` (Pitfall 3).
- `loadResolvedWatches`: `loadWatches` then `resolveWatches`, reading `process.env.RIDB_API_KEY` here and passing it as `ridbApiKey` if non-empty. This is the ONLY place `RIDB_API_KEY` is read. Never log the key's value.
- Default `logger` is `console`; tests inject a recorder.

Create `src/run.ts` — the single deployment-agnostic pipeline function (ARCHITECTURE.md Pattern 1). Phase 2 will call this same function from a GitHub Actions job and attach email delivery to its return value without changing its shape (D-07).

```typescript
export interface RunDeps {
  loadResolved?: () => Promise<ResolveResult>;                 // default: loadResolvedWatches()
  fetchRange?: (facilityId: number, start: string, end: string) => Promise<RawAvailabilityResponse[]>;  // default: fetchAvailabilityForRange
  store?: StateStore;                                          // default: new FileStateStore()
  logger?: { info(msg: string): void; warn(msg: string): void; error(msg: string): void };  // default: console
  now?: () => Date;                                            // default: () => new Date()
}

export async function run(deps?: RunDeps): Promise<RunSummary>;
```

Pipeline, in order:
1. `startedAt = now().toISOString()`.
2. `const { resolved, failures } = await loadResolved()`. A thrown config error propagates (fatal — nothing to poll).
3. `await store.load()`.
4. Seed `outcomes` with a `FAILED` outcome for every entry in `failures` (resolution failures are still reported per-watch, not swallowed).
5. For each `watch` of `resolved`, sequentially, inside its own `try/catch` (D-06):
   - `const responses = await fetchRange(watch.facilityId, watch.dateRange.start, watch.dateRange.end)`
   - `const slots = mergeSlots(...responses.map(parseAvailability))`
   - `const matches = matchWatch(slots, watch)`
   - If `matches.length === 0` -> push `{ watchId, status: 'NO_MATCH' }`.
   - Else split matches by `store.has(dedupKey(watch.id, m.campsiteId, m.startDate, m.endDate))` into `suppressed` (already seen) and `newMatches`. For each new match call `store.markNotified(key, now())`. Push `{ watchId, status: 'MATCH', newMatches, suppressed }`.
     - Note: if ALL matches are suppressed, still emit a `MATCH` outcome with an empty `newMatches` array — the run did find availability, it just isn't new. Do not downgrade it to `NO_MATCH`; that would make the logs lie about what the API returned.
   - `catch (err)` -> push `{ watchId, status: 'FAILED', reason: describeFailure(err) }`.
6. `await store.save()` in a `finally`-style position so it runs even if every watch failed.
7. Emit exactly one log line per outcome (D-07 — exact wording is Claude's discretion; these are the required prefixes and fields):
   - `OK    ${watchId} — ${newMatches.length} new, ${suppressed.length} already notified: ${sites}` (use `logger.info`)
   - `NO MATCH ${watchId} — checked ${nightCount} nights, nothing available` (use `logger.info`)
   - `FAILED ${watchId} — ${reason}` (use `logger.error`)
8. Build and return the `RunSummary`: `checked` = `resolved.length + failures.length`, `newMatches` = flattened new matches across outcomes, `failed` = every FAILED outcome as `{ watchId, reason }`, `noMatch` = watch ids of NO_MATCH outcomes, `finishedAt = now().toISOString()`.

Critical distinction to preserve (POLL-04): `noMatch` means "checked successfully, nothing available"; `failed` means "could not check". A watch id must never appear in both.

**`src/cli.ts`** — a thin trigger adapter with NO business logic (ARCHITECTURE.md: the same `run()` must work identically under GitHub Actions in Phase 2):

```typescript
#!/usr/bin/env node
import { run } from './run.js';
```
Behavior:
- Parse argv with `node:util.parseArgs` (no CLI-parsing dependency):
  - `--loop` (boolean): keep polling on an interval instead of exiting after one cycle (POLL-01 / ROADMAP success criterion 3)
  - `--interval <seconds>` (default `300`): delay between cycles in loop mode. Reject values below `60` with a clear error — polling faster than a minute risks IP/key blocking and is explicitly out of scope per REQUIREMENTS.md.
  - `--once` (boolean, default behavior): single cycle then exit
- One-shot mode: `const summary = await run()`, then print a final line `checked N — M new matches, K failed` and exit with code `0` if `summary.failed.length === 0`, else `1` (a non-zero exit makes a failed cycle visible to any scheduler).
- Loop mode: run cycles forever with `await run()` inside a try/catch (a fatal config error logs and exits `1`; anything else logs and continues to the next cycle so a transient problem never kills the loop). Between cycles `await setTimeout(intervalSeconds * 1000)` using `node:timers/promises`. Print a `--- cycle N at <ISO> ---` header before each cycle. Handle `SIGINT` by logging `stopping` and exiting `0`.
- No `try { ... } catch { process.exit(0) }` swallowing: a fatal error must exit non-zero.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Tampering | `loadWatches` in `src/config/watches.ts` | mitigate | Config is parsed with `WatchesFileSchema` before any value reaches a URL, a dedup key, or the matcher; failures throw with the offending zod issue path. Watch ids are schema-enforced unique, so no watch can collide with another's dedup namespace. |
| T-04-02 | Information Disclosure | `RIDB_API_KEY` handling | mitigate | The key is read in exactly one place (`loadResolvedWatches`), passed as `ridbApiKey` into the client's header construction, and never interpolated into a log line, error message, or the run summary. `describeFailure` (plan 01) is header-free by construction. |
| T-04-03 | Denial of Service | CLI `--interval` | mitigate | Loop mode rejects intervals below 60 seconds, and watches are polled sequentially with capped retries — bounding request rate against the undocumented endpoint, which REQUIREMENTS.md explicitly scopes out sub-minute polling to avoid IP/key blocking. |

| T-04-05 | Denial of Service | loop mode error handling | mitigate | Non-fatal cycle errors are caught and logged, and the loop continues to the next interval; only a fatal config error exits (non-zero). One bad cycle can never silently end unattended polling. |
