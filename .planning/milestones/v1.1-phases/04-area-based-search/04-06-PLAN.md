<objective>
Restructure `src/run.ts` from a flat `for (const watch of resolved)` loop into group-then-aggregate,
so an area watch's N resolved facilities collapse into exactly ONE `WatchOutcome`, and carry the
standard-vs-group tag through the matcher into both the log and the email digest.

load-bearing structural change of Phase 4 and the invariant it must preserve.

```typescript
  // ARCHITECTURE.md Anti-Pattern 2: an AreaWatch contributes N ResolvedWatch entries
  // sharing one id, but every runs.json consumer does outcomes.find(o => o.watchId === id).
  // Collapse to exactly ONE outcome per watch id before anything downstream sees it.
  const groups = new Map<string, ResolvedWatch[]>();
  for (const w of resolved) {
    const arr = groups.get(w.id) ?? [];
    arr.push(w);
    groups.set(w.id, arr);
  }

  for (const [watchId, facilities] of groups) {
    const allMatches: MatchedSlot[] = [];
    const facilityFailures: FacilityFailure[] = [];

    for (const facility of facilities) {
      try {
        const responses = await fetchRange(facility.facilityId, facility.dateRange.start, facility.dateRange.end);
        const slots = mergeSlots(...responses.map(parseAvailability));
        allMatches.push(...matchWatch(slots, facility));
      } catch (err) {
        // RESEARCH.md Open Question 3 — RESOLVED: degrade gracefully. One flaky campground
        // must never hide matches found on its 14 healthy siblings. This extends
        // resolveWatches()'s "a failure never aborts the run for the others" convention
        // one level deeper, from per-watch to per-facility.
        facilityFailures.push({
          facilityId: facility.facilityId,
          facilityName: facility.facilityName,
          reason: describeFailure(err),
        });
      }
    }

    const extra: { truncated?: TruncationInfo; facilityFailures?: FacilityFailure[] } = {};
    const truncated = truncationByWatch.get(watchId);
    if (truncated) extra.truncated = truncated;
    if (facilityFailures.length > 0) extra.facilityFailures = facilityFailures;

    // Every facility failed => the watch genuinely failed. Some failed => still report
    // what was found, with the failures attached.
    if (facilityFailures.length === facilities.length) {
      outcomes.push({
        watchId,
        status: 'FAILED',
        reason:
          facilities.length === 1
            ? (facilityFailures[0]?.reason ?? 'unknown failure')
            : `all ${facilities.length} campgrounds failed; first: ${facilityFailures[0]?.reason ?? 'unknown failure'}`,
        ...extra,
      });
      continue;
    }

    if (allMatches.length === 0) {
      outcomes.push({ watchId, status: 'NO_MATCH', ...extra });
      continue;
    }

    const newMatches: MatchedSlot[] = [];
    const suppressed: MatchedSlot[] = [];
    for (const match of allMatches) {
      const key = dedupKey(match.watchId, match.campsiteId, match.startDate, match.endDate);
      if (store.has(key)) {
        suppressed.push(match);
      } else {
        store.markNotified(key, now());
        newMatches.push(match);
      }
    }

    outcomes.push({ watchId, status: 'MATCH', newMatches, suppressed, ...extra });
  }
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Aggregated outcomes -> `runs.json` in a PUBLIC repo | Every consumer (dashboard, future tooling) assumes exactly one outcome per watch id per run; failure text must carry no credential |
| Availability API -> match loop | N times more untrusted responses per run than in v1.0, each one a chance to abort the cycle |
| Dedup store -> notification | A key collision would either spam the user or silently suppress a real opening |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-21 | Tampering | Duplicate `watchId` in `outcomes` | mitigate | The `Map<string, ResolvedWatch[]>` group-then-aggregate structure makes one outcome per watch id structurally guaranteed rather than incidental, closing ARCHITECTURE.md Anti-Pattern 2. Asserted directly by `outcomes.filter((o) => o.watchId === 'sierra').length === 1` |
| T-04-06 | Denial of Service | One failing facility inside an area watch | mitigate | The per-facility `try/catch` records a `FacilityFailure` and continues, so a transient `HttpError` on campground 7 of 15 cannot hide real openings on the other 14. `status: 'FAILED'` is reserved for the case where every facility failed, so a genuine outage is still reported honestly rather than masked as `NO_MATCH` |
| T-04-20 | Information Disclosure | `FacilityFailure.reason` written to `runs.json` in a public repo | mitigate | Every reason goes through `describeFailure`, documented and tested to never emit request headers or an `apikey`; the aggregate reason string adds only a facility count |
| T-04-22 | Repudiation | Duplicate notification across facilities | mitigate | `dedupKey(watchId, campsiteId, startDate, endDate)` is unchanged and `campsiteId` is globally unique across facilities, so the same campsite surfacing from two facilities in one group is suppressed by the existing store. `src/state/store.ts` is deliberately untouched — asserted by a `git diff --stat` acceptance criterion |
| T-04-16 | Repudiation | Group campground presented as a standard site | mitigate | The `[GROUP]` tag in the email section header and `MatchedSlot.facilityType` in `runs.json` make the distinction explicit; the user's stated use case is 1-2 tent sites |
| T-04-23 | Denial of Service | `checked` miscount misleading the dashboard | mitigate | `checked: groups.size + failures.length` counts watches, preserving the meaning every existing dashboard consumer already assumes; a facility-count semantic would silently inflate the number by up to 20x per area watch |
</threat_model>
