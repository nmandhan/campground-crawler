# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — extends the existing plain CSS in `dashboard/app/globals.css` (no Tailwind/shadcn installed; `dashboard/package.json` confirms only `next`, `react`, `react-dom`, `zod`) |
| Preset | not applicable |
| Component library | none — plain React client components with controlled inputs; modal and delete-confirm use the native `<dialog>` element (RESEARCH.md Pattern/Alternatives: gets focus-trap + Escape-to-close for free, zero JS, fits the zero-dependency posture) |
| Icon library | none — carried forward from Phase 3; new affordances (chip remove, toggle) use text/symbol characters (e.g. `×`) styled via CSS, not an icon font/SVG library |
| Font | unchanged system font stack: `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif` |

**shadcn gate result:** `components.json` not found; tech stack is Next.js. Per the shadcn initialization gate, this would normally prompt. **Declined for this phase** based on strong existing-project signal rather than re-prompting for a decision already effectively made: Phase 3 explicitly declined shadcn/Tailwind and established a plain-CSS, zero-dependency design-token system (`globals.css`, `03-UI-SPEC.md`) that is still the codebase's only styling layer; RESEARCH.md's own "Alternatives Considered" and "Don't Hand-Roll" sections for this phase explicitly recommend native `<dialog>` over any component library and warn against reaching for dependencies the project doesn't already have (CLAUDE.md: reuse `zod`, no new frameworks without cause). Introducing shadcn now would require also adding Tailwind, which this project has deliberately avoided across two prior phases. This phase's forms are simple enough (toggle, typeahead, chips, list, dialog, toast) to build with the existing token system extended below. **Registry safety gate: not applicable** (no shadcn, no registries).

**Rationale:** Consistency with Phase 3/4's established convention outweighs the marginal velocity gain of a component library for a ~6-component surface (toggle, typeahead input, chip, preview list, dialog, toast) that reuses this phase's own existing `.section`/`.row`/`.badge` primitives almost entirely as-is.

## Spacing Scale

Reuses Phase 3's declared scale exactly — no new tokens needed:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Chip internal padding, icon-text gaps, badge padding (unchanged) |
| sm | 8px | Gap between chips, gap between form label and input, compact list spacing |
| md | 16px | Default spacing between form fields, gap between watch-list row and its edit/delete buttons |
| lg | 24px | Padding inside the modal/dialog body, padding inside the preview panel |
| xl | 32px | Gap between major modal sections (location picker / date+site-type / preview) |
| 2xl | 48px | Unchanged (space between page header and first section) |
| 3xl | 64px | Unchanged (page-level margins) |

Exceptions:
- **44px minimum touch target** for the chip-remove `×` control and the edit/delete icon-buttons on each watch row — this phase introduces the dashboard's first genuinely interactive/clickable controls (Phase 3 had none), so tap-target sizing now applies where it previously didn't.
- **Toast/banner** (D-12) is a fixed-position element outside the normal document flow; use `--space-lg` (24px) padding and position `24px` from the viewport edge — not part of the 8-pt content flow but still a multiple of 4.

## Typography

Reuses Phase 3's exact 4 sizes / 2 weights — no new sizes or weights introduced:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Meta/timestamp (chip sub-label, toast, helper text) | 14px | 400 | 1.5 |
| Body (form inputs, watch-list rows, typeahead suggestions, preview list rows) | 16px | 400 | 1.5 |
| Section/modal heading ("Create Watch", "Edit Watch", section labels) | 20px | 600 | 1.2 |
| Page title (unchanged, "Campground Crawler — Status") | 28px | 600 | 1.2 |

Exactly 4 sizes, 2 weights (400 regular, 600 semibold) — matches Phase 3's contract; the new UI surface (forms, modal, toast) must not introduce a 5th size or a 3rd weight.

## Color

Reuses Phase 3's exact palette — no new hex values introduced, only new usage sites for the existing tokens:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Page background, modal/dialog background |
| Secondary (30%) | `#F1F3F5` | Section card backgrounds (unchanged), preview-panel background, chip background, disabled/locked state background |
| Accent (10%) | `#2563EB` | Reserved exclusively for: page/section heading text (unchanged), the primary "Save Watch" CTA button, the active state of the Facility/Area toggle, and the typeahead's focused-input border |
| Destructive | `#DC2626` | Reserved exclusively for: the "Delete" button/icon on each watch row, the delete-confirmation dialog's confirm button, and inline form-validation error text |

Accent reserved for: heading text, the primary Save CTA, the selected Facility/Area toggle segment, and focused-input border only — never used for chip backgrounds, secondary buttons ("Cancel"), or decorative elements.

**Additional semantic status colors** (unchanged from Phase 3, reused as-is inside this phase's new "[GROUP]" tag on preview rows):

| Status | Color | Usage |
|--------|-------|-------|
| standard campground tag | `#6B7280` (neutral gray, same as NO_MATCH) | Preview-list row tag for a standard campground |
| group campground tag | same `#6B7280` neutral, text reads `[GROUP]` per existing `derive-active-matches.ts` convention | Preview-list row tag for a group campground — distinguished by label text, not a new color, to avoid inventing a 4th semantic color |
| truncation warning | `#DC2626` (Destructive, reused) | "showing 20 of 34" warning text under the preview list when the shared 20-facility cap is hit |

No new colors are introduced anywhere in this phase.

## Interaction Notes (phase-specific, beyond the standard template)

These capture UI states the checker/executor need that aren't pure tokens/copy:

- **Unlock prompt (D-02):** renders inline where the management controls would be, replacing `+ Add Watch` and each row's edit/delete buttons with the unlock form. The read-only watch list itself (MGMT-01) renders identically whether unlocked or not.
- **Modal (D-04):** native `<dialog>` opened via `.showModal()`; Facility/Area toggle (D-05) at the top swaps the location-picker section below it — date range and site type fields never move position when the toggle changes, only the location section swaps.
- **Chips (D-06):** rendered as a wrapped row of pill-shaped elements (`--space-xs` internal padding, `--color-surface` background, `1px solid --color-border`), each with a trailing `×` remove control sized to the 44px touch-target exception above.
- **Typeahead (D-07):** debounced ~300ms, dropdown appears below the input, keyboard-navigable (arrow keys + Enter), closes on selection or blur.
- **Preview (D-09/D-10):** re-fetches automatically on every chip add/remove; shows a brief loading state (see copy above) rather than a spinner icon (no icon library); full list, not a count, each row tagged per the color/copy contract above.
- **Delete confirm (D-11):** a second, smaller native `<dialog>` (not the edit modal) — confirm button reads `Delete` and uses the Destructive color; cancel button reads `Keep Watch` and uses a neutral/secondary style (no accent).
- **Toast (D-12):** fixed-position banner, `--color-surface` background, `--color-text` text, auto-dismisses after ~4s or on manual dismiss; does not block interaction with the page underneath (not a modal).
- **Focal point (watch-list screen):** when unlocked, the `+ Add Watch` CTA is the primary visual anchor (top-right of the watch-management section, accent color, per Color contract above); when locked/read-only, the watch list itself is the anchor and the unlock prompt (D-02) is secondary.
- **Icon-button aria-labels (per watch row):** mirrors the chip-remove `aria-label="Remove {area name}"` pattern — edit button uses `aria-label="Edit watch: {watch name}"`, delete button uses `aria-label="Delete watch: {watch name}"`.
