<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Vercel build pipeline -> repo | A third-party build service is granted read access to the GitHub repo |
| Public internet -> deployed page | Anyone with the URL can read everything the page renders (D-04, no auth) |
| Deployed server -> raw.githubusercontent.com | Request-time egress to a public CDN with no credential |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-20 | Information Disclosure | A secret (`RESEND_API_KEY`, `RIDB_API_KEY`) being pasted into Vercel's environment variables "because the project needs config" | mitigate | Task 2 instructs explicitly: **add no environment variables**. `dashboard/lib/github.ts` reads no `process.env` at all (grep-asserted in plan 03-02, threat T-03-04), so there is nothing for a variable to configure. Any `NEXT_PUBLIC_*` variable would additionally be inlined into the client bundle. |
| T-03-21 | Elevation of Privilege | Vercel's GitHub app being granted write access or org-wide scope beyond what a read-and-build needs | mitigate | Task 2 imports a single repository. Vercel needs only read access to build; no deploy hook, no workflow write-back, and no GitHub Actions integration is configured (D-03 explicitly rules out deploy-hook integration). |
| T-03-22 | Tampering | The Vercel build reaching outside `dashboard/` and pulling the poller's dependency tree (or its `.env`) into the deployment | mitigate | Root Directory is set to `dashboard` and "Include source files outside of the Root Directory" is left off (Task 2 step 3). Plan 03-02 already guarantees the dashboard imports nothing from `src/`. Task 1 verifies a clean `npm ci` inside `dashboard/` succeeds standalone. |
| T-03-23 | Information Disclosure | The live deployment rendering fetch/parse diagnostics that the local SSR smoke test in plan 03-04 did not catch (different network path, real 429/404 responses from GitHub) | mitigate | Task 3 re-runs the leak checks against the deployed HTML: no `raw.githubusercontent.com`, no `HTTP 4`/`HTTP 5`, no `ZodError`, no stack frames. A live `Unable to load dashboard data` is treated as a failure of this task, not a pass. |
| T-03-24 | Tampering | An off-domain or `javascript:` booking link surviving to production | mitigate | Task 3 asserts every booking `href` in the served HTML starts with `https://www.recreation.gov/`, re-validating plan 03-03's `safeBookingUrl` allowlist against real data rather than fixtures. |
| T-03-25 | Spoofing | No authentication on a publicly-indexed URL | accept | D-04 locks "public, no auth"; the repo and every rendered field are already public. The page exposes no write action and no credential. |
| T-03-26 | Denial of Service | Crawler or shared-Vercel-IP traffic triggering rate limiting on raw.githubusercontent.com (RESEARCH.md assumption A1) | accept | The `next: { revalidate: 30 }` Data Cache window bounds outbound requests to roughly one per file per 30s regardless of page traffic. Documented escape hatch if 429s are ever observed: a token-authenticated fetch. Not pre-implemented — unverified risk, cheap fix. |
</threat_model>
